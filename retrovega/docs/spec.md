# RetroVega engine specification

Version 0.1, 2026-10-19. Working title, see [../README.md](../README.md).

RetroVega is a new single-player DOS space-combat game. Its engine is written
from scratch. It is built so that the multiplayer hook layer in this
repository (`src/cpu/wcnet_*`) can drive it the way it drives WC.EXE:

- the same named data with the same units, types, strides and enum values;
- the same far cdecl calls;
- the same hook contracts.

Nothing here comes from Wing Commander's code. The contract is taken only
from our own hook layer: what it reads, writes and calls (`wcnet_ds.def`,
`wcnet_code.h`, `wcnet_vm.*`, `wcnet_events.cpp`, `wcnet_hooks.cpp`).

## 1. Platform

| | |
|---|---|
| CPU mode | 16-bit real mode, 386 instructions allowed (32-bit registers, `movsd`) |
| Memory model | medium: far code, near data; SS == DS == DGROUP (the layer reads stack arguments through DS) |
| Toolchain | Open Watcom 2 (`wcc -mm -3`, `wlink`) for C, NASM (`-f obj`) for RVHOOK and the inner loops. Neither is installed yet; Open Watcom 2 has a Linux-hosted build. |
| Expanded memory | EMS 4.0 through int 67h, up to 32 MB = 2048 pages of 16 KB. That is exactly DOSBox's own ceiling (`EMM_MAX_PAGES` in `src/ints/ems.cpp`). |
| DOSBox config | `machine=svga_s3`, `ems=true`, `xms=true`, `memsize=40` (EMS is carved from extended memory) |
| Overlays | none: code stays resident and EMS holds the data, so every hook place is a root-image place (the layer's `root()`) |
| Executable | `RV.EXE` (the layer matches the file name and a signature; renaming the project changes one line in `kGames`) |

Conventional memory budget (DOSBox leaves about 630 KB free):

| what | KB |
|---|---|
| RVHOOK (thunks, flight-loop skeleton) | 4 |
| DGROUP: fixed block 32 KB + C data + 8 KB stack | 64 |
| code | ≤ 192 |
| 640×400 back buffer (4 bands of 100 rows × 640 = 64,000 bytes) | 250 |
| sound DMA double buffer | 8 |
| far heap: engine-private per-slot state, render lists | 48 |
| **total** | **≈ 566** |

## 2. Why the entity table moves (and stays put from then on)

WC.EXE has 64 entity slots, not 32. Only 10 of them (0..9) can hold ships,
capital ships or missiles. The rest hold bolts, explosions and dust, and the
last three are the camera and scratch. The "entity table" is about 30
parallel arrays, one element per slot, packed back to back from DS:A9C2 to
about DS:D26C.

With 128 slots every array doubles in size and would run into the next one,
so WC.EXE's offsets cannot be kept. What is kept is everything the layer's
code depends on:

- the names;
- the element types, sizes and strides (12-byte vectors, the 0x33-byte gun table);
- the units;
- the EntityType numbers;
- the meaning of 0xff / 0xffff;
- the slot roles.

The new offsets are fixed for good. `abi/rvabi.def` is their single source,
and the build fails if a link moves anything. The layer is already
table-driven, one column of `wcnet_ds.def` per executable plus a
`GameParams` row, so RV.EXE is one more column, written once.

## 3. Image layout

| image paragraph | contents |
|---|---|
| 0x0000 | **RVHOOK**, 4 KB: `"RVHOOK"` header, thunks from 0x20 (5 bytes each, `jmp far`), the flight-loop skeleton with its sites from 0x400 |
| 0x0100 | **DGROUP**: its first 32 KB is the fixed block of section 4, then C data, BSS, stack |
| after DGROUP | C code segments, any order and size |

How the layer recognises the program (`kGames` row):

- exe `RV.EXE`;
- `dgroupPara` 0x0100;
- signature `"Loading RETROVEGA"` at DS:0x0400, the start of `aLoadingWingCom`, just as WC.EXE's signature sits in its own scratch buffer.

`wlink` gets an explicit `ORDER` clause. A post-link check compares the map
file with `tools/rvabi.py --header` and fails on any difference.

### 4.1 Header (DS:0x0010, 48 bytes)

| offset | content |
|---|---|
| +0 | `"RVPUPPET"` |
| +8 | ABI version (word, 1) |
| +10 | slots (128) |
| +12 | max ship slot |
| +14 | first temp slot |
| +16 | camera slot |
| +18 | mission-ship record size |
| +20 | nav-point record size |
| +22 | gun-table size |
| +24 | gun record size |
| +26 | video mode |
| +28 | build number (dword) |
| +32 | 16 bytes of build date |

`rvPuppetDirectory` repeats every offset of the tables above, in the
`rvabi.def` order, so the layer can verify a build in one loop.

### 4.2 Slots

| slots | holds |
|---|---|
| 0 | the local player |
| 1 .. MAXSHIPSLOT | ships, capital ships, missiles |
| MAXSHIPSLOT+1 .. 124 | temporaries: bolts, explosions, debris, dust, engine glows |
| 125 | camera |
| 126 | spare |
| 127 | scratch vector |

The last-three convention (camera = slots-3, scratch = slots-1) is WC.EXE's;
the layer computes it from `GameParams.slots`.

MAXSHIPSLOT is a build constant:

- **9** for bring-up, exactly WC.EXE's partition. With 9 the layer needs no slot changes.
- **47** once the layer takes it from `GameParams` (5.3). That gives 48 ship-class entities and 77 temporaries.

### 4.3 EntityType (`maybeEntityType`)

These are the same numbers as WC.EXE. The layer compares them with `<` and
`>=`, so the order matters as well as the values.

| value | type | value | type |
|---|---|---|---|
| 0 | none | 8 | bolt |
| 2 | nav point | 9 | asteroid |
| 3 | nav icon | 0xA | mine |
| 4 | dust | 0xB | missile |
| 5 | explosion | 0xC | ship |
| 6 | sparkle | 0xD | capital ship |
| 7 | engine | | |

Ship types (`gInstanceShipTypes`) are the `type` column of
`data/ships.csv`. 0x16 and 0x17 mark asteroid and mine fields in a mission,
as in WC.EXE, so `GameParams.asteroidField` and `mineField` keep WC.EXE's
values.

Sides (`commAnimInfo`) are 0 Terran (the player's), 1 Aera and 2 Rlaan.
WC.EXE's AI already knows three sides: the player's, the enemy, and others.

### 4.4 Mission records

| record | layout |
|---|---|
| mission ship, 0x2a bytes | +0 ship type, +2 side, +4 leader, +6 behaviour. The rest is ours: +8 nav point, +10 position (3 × int16 km), +16 pilot, +17 AI skill, +18 flags, +20 cargo/objective, +22 name index, +24 .. reserved. |

The behaviour word at +6 uses WC2's meaning, which the layer relies on
through `missionShipAiOff`:

- 4 is an ordinary pilot flying in formation.
- 6 is the player, and is valid only for slot 0.

To spawn a copy of a human's ship as an AI-flown body on another machine,
the layer switches 6 to 4 around the `outerSpawnShipEntity` call
(`wcnet_events.cpp`). The engine must honour the word as it stands at that
moment.
| nav point, 0x4d bytes | the first 0x39 bytes are ours (position, type, triggers, scene); +0x39 holds ten mission-ship words (0xffff empty) |
| navPointState | 8 × 19 bytes of mission-tree progress |
| campaign table | 0x5A bytes per series (+2 missions, +3 points for the winning path, +0xA per-mission objective points) |

Ten ships per nav point is a WC.EXE limit that the layer hard-codes. RV
missions add ships beyond ten as later waves, each a nav record of its own,
until the layer takes the count from `GameParams`.

### 4.5 Gun table (`gunTable`, 0x33 bytes per slot)

| bytes | content |
|---|---|
| 1 | count |
| 10 × 5 | gun records |

Each 5-byte gun record:

| bytes | content |
|---|---|
| 2 | type word: a row of `data/weapons.csv` |
| 1 | mount x (int8, 1/32 of the ship's radius) |
| 1 | mount y (int8, same unit) |
| 1 | state: bit 7 destroyed; for a gun, bits 0-6 are cooldown frames; for a launcher, rounds left |

The layer copies records whole (`WeaponFire.gun` is exactly `gunSize` bytes).

### 4.6 GameParams for RV.EXE

`{ slots 0x80, missionShipSize 0x2a, classOff 0, classSize 2, asteroidField 0x16, mineField 0x17, navPointSize 0x4d, navPointShipsOff 0x39, missionShipAiOff 6, gunsSize 0x33, gunSize 5, campaign 0 }`

## 5. Code ABI

### 5.1 Thunks

Every hookable function is entered through a `jmp far` thunk at a fixed
offset in RVHOOK (the table in section 4). The engine's own callers go
through the thunk too (the C prototypes name the thunk; the body has an
`_impl` name), so a hook on the thunk sees every call.

All of them are `__cdecl __far` with 16-bit arguments. Pointer arguments are
near DS offsets. AX carries the return value. SI, DI, BP and DS are
preserved; AX, BX, CX, DX and ES are not.

That is exactly what the layer's `call_arg16`, `return_from_call` and
`GameCall` assume.

### 5.2 Sites

The flight loop's skeleton is hand-written in `rvhook.asm`. Each site sits
at its fixed offset with the same instruction pattern and register contract
as the WC.EXE place of the same name, so the layer's existing handlers run
unchanged:

| site | contract |
|---|---|
| `mainLoopTop` | Interrupts are on, no live registers except SI, DI and BP. The world is consistent, so a trampoline job may spawn, fire, damage or despawn here. The layer finds a new frame by watching `frameCounter`. |
| `statusSetByExitKey`, `statusCheckAfterKeys`, `statusCheckAfterFrame` | Just before `cmp word [missionStatus],0 / jne leave`. The layer may have written `missionStatus`, and a nonzero value must end the loop. |
| `skipOrchestra`, `autopilotKey` | A 5-byte `call far` that the layer may step over (IP += 5). |
| `cockpitPointer` | A 4-byte `call far [mem]`; the caller cleans up. |
| `autoAnimationBody` | After `push bp / mov bp,sp` in autoAnimation's asm prologue; the arguments are at `[bp+6]`, `[bp+8]` and `[bp+0Ah]`. |
| `afterStartup`, `afterHangarMission` | Return points in the same segment as `runHangarMission`'s caller. |

### 5.3 What the layer has to learn

These are the places where RV.EXE differs on purpose. Each is a small,
contained change to `src/cpu/`.

1. **Register the build.** Add `BUILD_RV`, a seventh `wcnet_ds.def` column (from `tools/rvabi.py --column`), a `kGames` row, `load_rv_code()` using `root()` only, and `kRvParams`.
2. **Pick a GameId.** Make a new `GAME_RV` that shares WC1's per-frame pacing (`wcnet_perf.cpp`: 20 fps) and seat logic. Use helpers such as `is_wc1_like()` rather than reusing `GAME_WC1`, because some WC1 branches write raw WC.EXE offsets.
3. **Function forms.** Three WC.EXE mid-function places become thunks:
   - `farShipTest(slot, km)` replaces the two `cmp ax,imm16 / jng` sites;
   - `aiSetSpeed(ship, speed)` is skipped with `return_from_call`, not an IP jump;
   - `despawnQuietly(slot)` replaces the raw offsets in `despawn_slot_quietly` (`wcnet_events.cpp`).
4. **More than 9 ship slots** (phase 2):
   - move `kMaxShipSlot` and `kMinTempSlot` into `GameParams`;
   - turn the fixed snapshot arrays into vectors;
   - widen the 32-bit predicted-missile mask;
   - replicate slots 0..max ship slot rather than 0..9.
5. **640×400 cosmetics.** The screenshot, `!vga`, the helmet name and cockpit dimming read mode 13h memory; they should look at `rvVideoMode`. Steering needs nothing, because RV keeps `viewRect`, `steerSteps*` and the mouse in logical 320×200 coordinates in both modes (section 7).
6. **Optional.** These replace heuristics with explicit state:
   - `setController` and `rvController` instead of skipping the AI hooks per call;
   - `rvFlags` bit 2 (local-only hazard) instead of `is_local_hazard`'s parent walk;
   - `rvNetId` instead of the `EntityMap` lookups.

## 6. Simulation rules the layer relies on

1. **Fixed step.** One frame is one simulation step at 20 per second. `frameCounter` goes up by one per frame and nothing else changes it. Velocity is the position change per frame. `setSpeed` and `speedLo` are kps; the engine converts them (1 kps = 12.8 position units per frame). No variable timestep anywhere.
2. **State lives in the arrays.** The layer writes positions, orientations, health and gun records between frames. The engine keeps no cache keyed on them: derived state is recomputed from the arrays each frame, and orientation vectors are re-orthonormalised every frame (the layer writes 1.0 = 256 values that drift).
3. **One random stream.** All gameplay randomness comes from `randomSeed`, which the layer re-seeds before replaying a spawn or a hit. Purely visual randomness (star twinkle, spark spread) uses a second seed outside the ABI, so drawing never desynchronises play.
4. **Controllers.** The engine reads `rvController` every frame.
   - 0 (AI) runs `aiFighterThink` or `aiShipThink`.
   - 1 (the local player) reads input.
   - 2 (puppet) does neither. It only coasts (position += velocity) until the layer writes the slot again (`rvLastWrite`).
   - 3 (script) runs the mission script.
   - 4 (frozen) does nothing.
5. **Re-entrancy.** Every thunk may be called from `mainLoopTop` with interrupts on. No thunk relies on the caller's registers. Spawning and despawning from a thunk are complete when it returns.

## 7. Video

| | high resolution | low resolution |
|---|---|---|
| mode | VESA 100h, 640×400×256, 64 KB bank windows (bank switch through the VBE window function, not int 10h) | 13h, 320×200×256 |
| back buffer | conventional memory, 4 bands of 100 rows (a row never straddles a segment) | one 64,000-byte segment |
| flip | dirty rows only, split at the 64 KB bank boundaries (row 102 straddles banks 0 and 1) | `rep movsd` |
| sprites | LOD0 as in `ships.csv` `lod0_px` | one LOD step down |
| cycles target | 40,000 (486DX2/DX4 class) | 16,000 (WC.EXE's flight setting) |

`viewRect`, the comm VDU rectangle and the steering tables are always
written in *logical* 320×200 coordinates. The mouse range is set to 640×200
(int 33h functions 7 and 8) with `mouseShift` = 1, as in WC2. The engine
doubles y itself in high resolution. The layer's pointer and steering
arithmetic therefore works in both modes without change.

**Performance gate (milestone M2).** Measure a full 640×400 frame with 6
fighters, 2 capital ships and 40 bolts, in the browser build as well as
natively (the browser is the binding constraint). If it misses 20 fps at
40,000 cycles, fall back in this order:

1. roll quantised to 16 steps, with LOD2 and LOD3 pre-rotated;
2. a smaller 3D view;
3. low resolution as the default for the browser.

## 8. Sprites and assets in EMS

**The view layout is WC1's**, read from WC1's own ship files (`SHIPTYPE.Vnn`:
a block of 37 run-length sprites, then a hardpoint block and the ship's
record). Each ship has 37 pre-rendered views:

| index | view |
|---|---|
| 0 | top |
| 1..7, 8..14, 15..21, 22..28, 29..35 | elevation bands +60°, +30°, 0°, −30°, −60°; in each band, headings 0°, 30° .. 180° |
| 36 | bottom |

Heading 0 is the nose toward the viewer, 90 the profile with the nose to
the left, 180 the tail toward the viewer. Headings 210..330 draw the
mirror image of 150..30. The top and bottom views lie nose left. A sprite
is centred on the ship's origin and stored with WC's header: four int16,
x2, x1, y1, y2, giving the extent around the origin. Its body is WC's
run-length code, so `scripts/wc2data.py` (`encode_sprite`,
`decode_sprite`) reads and writes ours too.

Our order inside each band is the one above. WC1's own files use the same
37 slots but do not run every band front to back. If we ever want sprites
to move between the two games, a 37-entry remap table bridges them.

**Resolution: twice WC1's, one size.** WC1's fighter views are 60 to 100
pixels across on its 320×200 screen. Ours are rendered in a box of
`lod0_px`, 128 to 192 pixels for fighters. As in WC1, the engine scales one
set of views to the distance. A half-size copy for distant ships is
optional and decided at M2 by how much the scaling shimmers. The engine
chooses the view from the ship's heading and elevation relative to the
camera. Roll is drawn by the blitter (rotate and scale), so a view decoded
into EMS is stored uncompressed (one byte a pixel, 0 transparent) with a
row table.

**Hardpoints.** Gun mounts and engine positions come from Vega Strike's
`units.csv` (its `Mounts` and `Light` columns). The renderer already
places engine glows from `Light`. At M3 it also projects the gun mounts into
each of the 37 views, as WC1's per-view hardpoint block does, so muzzle
flashes and bolts start at the right pixel.

**Liveries.** Each sprite pixel is either hull or paint:

- primary paint (wingtips, large panels);
- secondary paint (stripes, accents).

Paint pixels are stored in two placeholder ramps of the palette (section 9).
A livery (`data/liveries.csv`: carrier green, Confed blue, militia red, ace
gold, ...) is a recolouring of those two ramps. It is applied when a ship
type's views are decoded into EMS for a mission, once per (type, livery)
the mission uses, so flying costs nothing. The slot's `rvLivery` byte names
the livery, so every machine in a flight shows the same colours, and a
human's own choice travels with their spawn.

EMS budget per mission (32 MB in all):

| asset | each (decoded) | per mission |
|---|---|---|
| fighter type × livery: 37 views at 128-192 px, cropped | 0.3-0.7 MB | the player's + 5 ≈ 3 MB |
| capital ship type: 37 views at 320-640 px, cropped | 1.5-5 MB | ≤ 4 ≈ 12 MB |
| explosions, bolts, debris | | 1 MB |
| cockpit (640×400 and its damaged overlay) | 0.5 MB | 0.5 MB |
| comm faces, VDU art | | 2 MB |
| sound effects (8-bit 11 kHz) and music | | 2.2 MB |
| **total** | | **≈ 21 of 32 MB** |

A mission loads only the types it uses. On disk there is one archive
(`RV.DAT`) with an entry per ship (record, 37 run-length views, the
hardpoint block, VDU art), per cockpit, per mission and per sound bank.
The download size matters for the browser build.

Sound: the Sound Blaster plays 8-bit 11 kHz effects from a conventional
double buffer. The SB interrupt refills it from EMS, saving and restoring
the page map (int 67h functions 47h/48h). Music is OPL (AdLib/SB).

Input:

- the keyboard through our own int 9 handler (the layer injects keys through the emulated keyboard, so this is transparent);
- the mouse through int 33h;
- the joystick through port 201h.

## 9. Art direction and the renderer

The look follows WC1's Confed ships (`SHIPTYPE.V00`..`V03`): white or light
hulls with large saturated panels (green, red), accent stripes and hazard
bands on the wing edges. The lighting is that of 1990s pre-renders: a point
light up and to the left shades flat panels from bright to dark, with no
ink lines. Each faction keeps its character:

- Terran: white hulls in carrier liveries;
- Aera: steel and teal with glowing trim;
- Rlaan: charcoal and violet organic shapes.

**The renderer** (`tools/shipviews.py`, setup in [art.md](art.md)) is a
minimal headless OpenGL renderer (moderngl on Mesa). It draws each ship's
Vega Strike mesh (`.bfxm`, read by `tools/bfxm.py`) with its own diffuse,
specular and glow maps into the 37 views, 4× supersampled and boxed down.
Lighting:

- a warm point key light, a cool fill and a soft rim;
- hemisphere ambient;
- an optional banded key light for a cel look;
- matte paint, so liveries stay saturated.

Afterwards it adds:

- engine glows at Vega Strike's exhaust points, in the faction's colour (orange, cyan, magenta), where the exhaust faces the viewer and is not hidden;
- a darkened silhouette edge;
- light depth-based cavity shading.

It writes the views, a paint mask per view (1 primary, 2 secondary), a
sheet and a posterised preview.

**Per-ship art settings** (`data/art.csv`):

- **stretch:** scale x y z. The Franklin is thickened 1.8× in y; the Vega Strike mesh is a 0.6 m dart.
- **exposure.**
- **toon:** bands, 0 for smooth.
- **whiten:** how far the hull goes toward light grey, keeping the texture's panel detail.
- **paint rules** for the primary and secondary colours, combined with `|`:
  - `span>F`: beyond F of the half-span, i.e. wingtips;
  - `spine<F`: a stripe along the centre line;
  - `hazard>F`: bands beyond F of the half-span;
  - `lum>P`: panels brighter than the P-th fraction of the texels the mesh uses;
  - `fin>F`: vertical surfaces beyond F of the half-span (wingtip fins);
  - `band:A-B`: a stripe across the wings between A and B of the half-span;
  - `above>F`: everything higher than F of the ship's height;
  - `blue>D`: texels bluer than their red and green by D, i.e. a canopy painted navy in the Vega Strike texture;
  - any term may end in `@top` or `@bottom` to paint only the surfaces facing that way. The Franklin is `fin>0.95|band:0.55-0.7` in the primary colour and `spine<0.07@bottom` (a stripe under the belly) in the secondary.
- **glass:** a rule for the canopy, drawn dark navy and glossy in every livery. The Franklin's is `blue>0.12`, the oval dome on its nose taper.

**Palette** (one fixed 256-colour palette in flight):

| index | use |
|---|---|
| 0 | transparent / black |
| 1-15 | HUD and UI |
| 16-31 | hull whites and greys |
| 32-47 | Aera hull steels |
| 48-63 | Rlaan hull charcoals |
| 64-71 | livery primary (placeholder ramp) |
| 72-79 | livery secondary (placeholder ramp) |
| 80-87 | canopy glass, navy to highlight |
| 88-127 | the liveries' target ramps, 8 shades each: green, blue, red, gold, black. Aera teal and Rlaan violet liveries use their faction's hull ramps. |
| 128-143 | fire and explosions (cycled) |
| 144-151 | engine glow, Terran orange |
| 152-159 | engine glow, Aera cyan and Rlaan magenta |
| 160-223 | the scene block: the cockpit in flight, backgrounds and faces elsewhere |
| 224-239 | stars and nebula |
| 240-254 | comm-face skin |
| 255 | white |

The quantiser (M3) sends paint pixels (from the paint masks) to the
placeholder ramps by brightness, glass pixels to the glass ramp, and everything else to the nearest hull or
glow colour, without dithering. Until it exists, the renderer's `_256`
sheet is a 48-colour median-cut preview.

**VDU images** (`-hud` files, really DDS whatever the extension) become
the targeting VDU and briefing/ship-select art. They are posterised into
the palette and touched up by hand: 96 px in high resolution, 48 px in low.

**New Aera hulls** (Agis, Cleomenes, Archidamus) are mesh edits of
Nicander, Areus and Ariston, rendered by the same path. The Charillus'
tan hull takes an Aera livery. The Leonidas' VDU is only a silhouette, so
its art comes from the mesh.
